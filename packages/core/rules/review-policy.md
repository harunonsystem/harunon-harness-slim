## レビューポリシー

全レビュアー共通の判断基準と行動原則。

### 原則

| 原則 | 基準 |
| --- | --- |
| 即修正 | 軽微な問題を「次のタスクで」と先延ばしにしない。今直せるものは今直す |
| 曖昧さ排除 | 「この辺整理して」は禁止。ファイル、行、修正案を明示 |
| 事実確認 | 指摘前に実コードを確認。推測で指摘しない |
| 実践的な修正 | 理論的な理想ではなく、実装可能なソリューションを提案 |
| Boy Scout | 変更したファイルに問題があれば、タスク範囲内で修正させる |

### diff baseline の導出

「変更ファイル」の判定は baseline に依存するので、スコープ判定の前に baseline を確定する。

- 比較前に `git fetch origin <base>` する。stale な `origin/<base>` は base 側にある他人の変更を「変更ファイル」に混ぜ、diff 外の指摘を blocking として報告する（8 件中 5 件が diff 外だった実例: 2026-08）
- baseline は `git merge-base origin/<base> HEAD` で求める。`origin/<base>..HEAD` の 2 点比較は使わない
- `git diff --name-only <merge-base>..HEAD` の集合を「変更ファイル」とする。この集合に無いファイルの指摘は blocking にできず Out of scope に落とす

### スコープ判定

| 状況 | 判定 | アクション |
| --- | --- | --- |
| この変更で導入された問題 | ブロッキング | REJECT |
| この変更で未使用になったコード（引数、import、変数、関数） | ブロッキング | REJECT（変更起因の問題） |
| 変更ファイル内の既存問題 | ブロッキング | REJECT（Boy Scout Rule） |
| 変更モジュール内の構造的問題 | ブロッキング | スコープ内なら REJECT |
| 未変更ファイルの問題 | 非ブロッキング | 記録のみ（情報提供） |
| タスクスコープを大幅超過するリファクタリング | 非ブロッキング | 提案として記録 |

### REJECT 基準（必ず変更要求）

以下のいずれかに該当すれば例外なく REJECT:

- テストなしの新しい振る舞い
- 回帰テストなしのバグ修正
- `any` 型の使用
- フォールバック値の濫用（`?? 'unknown'`）
- 説明的コメント（What/Howコメント）
- 未使用コード（「念のため」コード）
- オブジェクト/配列の直接変更
- エラーの握りつぶし（空catchブロック）
- TODO コメント（issue で追跡されていないもの）
- 本質的に同一のロジックの重複（DRY違反）
- 同じことをするメソッドの乱立
- 汎用レイヤーに特定実装が漏洩
- 内部実装の公開APIへのエクスポート
- リファクタリング後に置換済みコード/exportが残存
- 関連フィールドのクロスバリデーション欠落

DRY指摘は統合先の妥当性も検証する。以下がすべて成り立たない限り統合提案は無効:
- 統合先が既存の責務境界と依存方向に合致
- 新しい公開API/ラッパー/ヘルパーが既存契約を不自然に拡大しない
- タスクやプランが要求しない抽象化を導入する場合、根拠を示す

### セキュリティ REJECT 基準

外部入力が危険な sink に未検証で到達する diff は REJECT。sink 詳細表は `skills/cr/references/security-sinks.md` 参照（レビュー時のみ読み込み）。

**スコープ判定**: 変更 diff が導入・変更した sink はブロッキング。未変更ファイルの既存 sink は非ブロッキング（記録のみ）。Severity は基本 `critical`。

### Warning 基準

ブロッキングではないが改善を推奨:
- 不十分なエッジケース/境界値テスト
- 実装詳細に結合したテスト
- 過度に複雑な関数/ファイル
- 不明確な命名
- 放置された TODO/FIXME（issue番号付きは可）
- 根拠なしの `@ts-ignore` / `eslint-disable`

### APPROVE 基準

以下のいずれかで APPROVE:

- Finding 0 件
- `critical` / `major` が 0 件で、`minor` のみ残存

`critical` / `major` が 1 件でも残っていれば REJECT。条件付き承認（conditional approve）はしない。`minor` は改善推奨として記録するが承認は可。

### 事実確認（Fact-Checking）

指摘前に必ず事実確認する。

| する | しない |
| --- | --- |
| ファイルを開いて実コードを確認 | 「修正されているはず」と仮定 |
| grep で呼び出し箇所と使用箇所を検索 | 記憶に基づいて指摘 |
| 型定義やスキーマとクロスリファレンス | コードがデッドだと推測 |
| 生成ファイル（レポート等）とソースを区別 | 生成ファイルをソースとしてレビュー |

### 具体的なフィードバックの記述

全ての指摘に以下を含める:
- **どのファイル、どの行番号か**
- **問題は何か**
- **どう修正するか**
- **抽象化や統合を要求する場合、なぜその配置が自然かの根拠**

```
NG: 「構造を見直して」
NG: 「この辺整理して」
OK: 「src/auth/service.ts:45 — validateUser() が3箇所で重複。共有関数に抽出。」
```

### Finding ID 追跡

循環拒否（circular rejection）を防ぐため、指摘を ID で追跡する。

#### ルール

- REJECT 内の全指摘に `finding_id` を付与する
- 同じ問題が再度発生した場合、同じ `finding_id` を再利用
- 繰り返し指摘にはステータス `persists` を設定し、未解決の根拠（file:line）を含める
- 新規指摘はステータス `new` を使用
- 解決済み指摘はステータス `resolved` でリストする
- `finding_id` なしの指摘は無効（REJECT の根拠にできない）
- `new` または `persists` の指摘が1つ以上ある場合のみ REJECT 可能
- 解決済みとする前に、修正が別の構造的/契約的問題を導入していないか確認

#### Reopen 条件（`resolved` → open）

解決済み指摘の再開には再現可能なエビデンスが必要:
1. 再現手順（コマンド/入力）
2. 期待結果 vs 実際の結果
3. 問題のあるファイル/行のエビデンス

3つのうち1つでも欠けたら再開は無効（REJECT の根拠にできない）。再現条件が変わった場合は別問題として新しい `finding_id` を発行する。

#### Finding ID の意味不変性

同じ ID に異なる問題を混ぜない:
- 1つの `finding_id` は1つの問題のみを指す
- 問題の意味、エビデンスファイル、再現条件が変わったら新しい `finding_id` を発行
- 既存の `finding_id` を別の問題を表すように書き換えることは禁止

### テストファイルのサイズと重複の扱い

テストファイルの長さと重複はデフォルトで Warning レベルの保守性の問題:
- 過度なテストファイル長と重複したテストセットアップはデフォルト `Warning`
- 再現可能な実害が示された場合のみ `REJECT`:
  - flakyな動作
  - 偽陽性/偽陰性
  - リグレッション検出不能
- 「長すぎる」「重複している」だけでは `REJECT` の根拠にならない

### 判定ルール

- 変更ファイル内で検出された全指摘はブロッキング（REJECT対象）。変更前からそのコードがあったとしても
- 変更対象でないファイルの指摘のみ「既存問題」「非ブロッキング」に分類可能
- 「コード自体は変更前から存在した」は非ブロッキングの理由にならない。変更ファイルにある限り Boy Scout Rule 適用
- `critical` / `major` が 1 件でも残っていれば REJECT。「条件付き APPROVE」「警告付き APPROVE」「提案付き APPROVE」は禁止
- `minor` のみの残存は APPROVE 可（改善推奨として記録）

### 循環論法の検出

同種の指摘が繰り返される場合、同じ修正指示を繰り返すのではなくアプローチ自体を再考する。

#### 同じ問題が再発した場合

1. 同種の指摘が繰り返されていないかチェック
2. 繰り返しなら、粒度の細かい修正指示ではなく代替アプローチを提案
3. REJECT する場合でも「別のアプローチを検討すべき」という視点を含める

「もう一度直して」を繰り返すのではなく、立ち止まって別の道を示す。
