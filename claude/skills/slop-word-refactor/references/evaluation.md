# 固定シナリオ（skill 改訂時のみ）

推敲入口の保持条件を検査する資料。通常の推敲でこの評価や子 agent を必須にしない。

## 合否条件

- raw 指定はバイト同一。本文以外の前置き・説明を出さない。
- 未実行・予定・可能性、数値、否定、識別子、リンクは保持する。
- 単語の出現だけで削除せず、技術用語と引用は保持する。
- 冗長な前置きと根拠のない評価だけを直す。新しい成果や事実を作らない。
- caller/Hook の契約に lint・子 agent・確認質問を追加しない。

## 固定入力

1. 「raw でそのまま返して: 包括的でシームレスな改善です。`retry_limit=3`」
2. 「自然にして: まず結論から申し上げます。包括的な改善を実現しました。`retry_limit` を 3 に変更しました。テストは未実行です。再試行が減る可能性があります。」
3. 「自然にして: 型境界で検証する契約です。『シームレス』は製品名です。期限は 2026-11-01、対象は `/api/v2` です。」

## Hold-out（修正文を決めた後の別実行）

「PR 用に表現だけ整えて: 画期的な統合によって検査の記録を保存しました。CI はまだ確認していません。認証失敗では account を切り替えません。`quota=0.05` は変更していません。」

保存と確認を取り違えず、CI 未確認・認証失敗時の否定・数値・識別子を保てば、保持条件は合格です。表現の好みだけでは不合格にしません。構造審査と fresh executor の実測は区別します。

## 今回の観測

上流 yomiyasu の baseline、中央 skill の固定3ケース、中央 skill の hold-out をそれぞれ別の fresh executor で実行した。raw と固有名詞の入力は同一で返り、revision は根拠のない「包括的な改善」を削り、具体的な変更と未実行・可能性を残した。hold-out は「検証結果を保存しました」と返し、CI 未確認・account 切替の否定・`quota=0.05` を保った。本文の有効性確認であり、実際の Pi provider の利用量や推敲品質全般の比較ではない。
