# slop-word-refactor

文章の表現だけを整える。手動の推敲、呼び出し元 skill、表示・保存 Hook はすべてこの契約を使う。旧 skill の連鎖実行や独立した二重推敲はしない。

## 保持するもの

- 事実、因果、否定、数値、条件、責任主体、不確実性、未確認事項、risk、残件を増減させない。予定を実施済み、可能性を断定に変えない。
- 識別子、ファイル名、パス、URL、引用、CLI flag、コード、frontmatter、Markdown/HTML の構造、template の見出し・checklist を保つ。
- `raw`・`そのまま`・`逐語`・`推敲しない` の依頼は処理しない。対象に指定されていない引用や英語を勝手に翻訳しない。
- 問題のない文章は変更しない。情報が足りなければ補って創作せず、不確実なままにする。

## 手順

1. 読み手、伝える結論、必要な前提を確認する。説明が通らないときは、まず口頭で「何がどうなるか」を説明できる順序にする。長くすること自体を目的にしない。
2. 曖昧な総称・大げさな評価・反復・前置き・自称ラベルを探す。文脈で不要と判断できる箇所だけ削るか、原文にある具体的な主体と動作で言い換える。
3. 原文と比較し、保持するものに変化がないか確認する。変更理由の説明を求められなければ、推敲済み本文だけを返す。

## 文脈で判断する表現

これは禁止語の辞書ではない。単語が現れただけで削らず、技術的な意味、固有名詞、引用として必要なら残す。

- 「包括的」「シームレス」「堅牢」「最適」「画期的」や comprehensive / seamless / robust: 根拠や具体的な対象がない評価なら、原文にある変更・保証範囲を書く。根拠を新しく作らない。
- 「活用する」「実現する」「〜を可能にする」「〜という形で」や leverage / facilitate: 単なる引き延ばしなら「使う」「〜する」など実際の動作にする。必要な意味の差は残す。
- 「まず結論から」「重要なポイントは」「以下に詳しく」「ぜひ〜」など: 内容を増やさない前置き・定型の締めなら省く。
- 唐突な否定対比、抽象語だけの短縮、主語のない受動文: 誰が何をするかを原文の範囲で明らかにする。条件や例外を削って短くしない。
- 「門」「検査の記録」「秘密」「証跡」: 開発・テストの報告で比喩や曖昧な表現なら「公開条件」「検証結果」「機密情報」「記録」など実態に合う語にする。実在の門、固有名詞、正式な監査用語は変えない。保存・記録・確認は別の動作なので取り替えない。「記録が完了した」を「確認した」に変えない。
- 「境界」「契約」「接続」「回収」「流す」「寄せる」「束ねる」「薄いラッパー」など: コードや設計で具体的な意味があれば保持し、動作を説明していない比喩だけ直す。

## 呼び出し元との役割分担

- `implement-issue` / `spec-ready` / 比較・質問: 要件・選択肢・判断材料は呼び出し元で確定し、ここでは表現だけ直す。確認質問や承認手順は追加しない。
- PR・Issue・commit: 差分の事実と template を先に確定する。PR では domain `business` として扱うが、別 skill を起動しない。公開承認・検証・本文 evidence の gate は省略しない。
- 記事: 論証構成やコードの実名調査は専門 workflow の責務。本文の脱 AI 臭だけをここで行う。
- 表示・保存 Hook: 呼び出し元が指定した編集可能範囲と出力形式を守り、構造保護・deadline・fallback の機構を変えない。参考資料を追加で読み込んだり、子 agent や CLI を起動したりしない。
- 既に同じ本文を処理した場合は検査だけに留め、再リライトしない。出力やファイルが変わった場合だけ差分を確認する。

## PR 本文の機械チェック

既存の公開ゲートが使う空句検出の正本。PR 本文だけが対象で、通常の会話・技術用語全体の禁止語辞書ではない。ゲートのコードはこの節を読み、独自の語句リストを持たない。code fence 内は検査しない。規則を変える場合は公開条件の変更として検証し、推敲側の都合で抑制しない。

<!-- pr-body-patterns -->
```json
[
  ["重要なのは", "予告の空句"],
  ["本章では", "章の予告"],
  ["ここでは.{0,24}(見ていく|扱う|探求する)", "内容の予告"],
  ["(?:まとめると|要するに)", "直前の総括"],
  ["正面から(?:扱う|回収する|見る|書く|立てる)", "姿勢の宣言"],
  ["(?:深掘り|掘り下げ)する", "内容のない動詞"],
  ["言語化する", "内容のない動詞"]
]
```

## 必要なときだけ読む資料

資料は skill として起動しない。旧 frontmatter、モデル指定、ユーザー確認、必須レビュー等の実行手順は採用しない。この本文の対象範囲と保持条件を優先する。

配布先では `../../references/writing/`、配布元では `packages/core/policy/writing-style.json` の source を参照する。public slim 等で資料が未配布なら、この本文だけで推敲する。資料の導入を要求して作業を止めない。

- `yomiyasu/SKILL.md` と `references/domains/business.md`: 日本語の主述対応、文末、PR 文体の例。
- `unslop/SKILL.md`: 英語を含む AI 特有の言い回しの例。
- `explain-before-shorten/SKILL.md`: 文脈不足な説明を意味を保って短くする例。
- `ja-writing/.textlintrc.json` と `package.json`: 文書の lint を明示的に依頼された場合や repo が要求する場合の設定資料。通常の会話や短い報告では実行しない。実行時は Bun と lockfile を使い、repo 独自設定を優先する。

textlint と子 agent レビューは常時必須ではない。原文の意味を変えて lint に合わせず、lint 規則の抑制・変更は repo の規約に従う。
