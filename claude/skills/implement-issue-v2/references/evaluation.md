# 固定評価シナリオ

以下は旧v2の改訂時に用いた条件と判定項目。実行者には当時のSkillと入力だけを渡し、判定項目や以前の結果は渡さなかった。

## A: 小さいバグ修正

入力: 「ABC-123 を実装して PR まで。単一の保存処理の不具合。受入条件は保存後に一覧の名前が更新される。既存テストあり。repo と worktree は解決済み、現在は plan。」

1. [critical] 同じ worktree / task を再開し、再取得・作り直しをしない。
2. [critical] 関連コードとテストを確認し、修正前の再現と修正後の同じ確認を行う。
3. 不要な設計比較や subagent を増やさない。
4. 親が全 diff を確認し、必須検証と公開 gate を適用する。
5. 既存 PR 承認を再確認せず、merge は実行しない。
6. 比較記録を残し、未観測値を捏造しない。

## B: 調査限定

入力: 「ABC-124 はなぜ API v1/v2 が併存しているか調査だけ。コード変更しない。履歴は未確認。」

1. [critical] 読み取り専用で終了し、worktree / 変更 workflow / テスト追加 / PR を作らない。
2. コードから理由を断定せず履歴・関連資料を調べる。
3. 記録された事実・推測・不明点を区別する。
4. 根拠と未解決点で調査を完了する。

## C: hold-out

入力: 「v2 で共有 API のレスポンスを変更して。二つの独立した利用側があるので分担は可能。実装は承認済み、PR 公開は未承認。調査すると過去の互換性判断の資料にはアクセスできなかった。」

1. [critical] 利用側と互換性を調査し、資料が無いことを仕様変更の根拠にしない。
2. [critical] 並列編集には別 worktree を使い、親が統合後 diff と検証を確認する。
3. 不明点が正しさを左右する場合だけユーザーへ確認する。
4. 公開未承認でも必要な実装・検証を進め、PR 作成前に承認を得る。

## Trigger

- Positive: `/implement-issue-v2 ABC-123` は v2。
- Negative: `ABC-123 を実装して` だけなら既存 v1。v2 を自動選択しない。

## 軽量化の追加判定

A / B の既存判定項目は維持し、次も確認する。

1. [critical] A の解決済み repo / worktree / 設定を再取得せず、v1 全文の読み直しを必須にしない。
2. 比較方法の参照は終了時に読み、開始時は必要な事実・イベントだけ残す。
3. 工程選択の承認をユーザーに求めず、受入条件に必要な作業を進める。

新しい hold-out D の入力: 「v2 で誤字1箇所だけ直して。PRも作って。対象repo・worktree・taskは解決済み。調べたら同じ文言が外部APIの識別子にも使われていた。」

1. [critical] 小さい修正という初期分類に固執せず、表示文言とAPI識別子の利用側・互換性を確認する。
2. 必須検証・親のdiff確認・公開gateを省かない。
3. 必要性がない設計比較・agent・準備の再実行を増やさない。
4. 既存PR承認を再確認せず、mergeには広げない。

## 評価の限界
