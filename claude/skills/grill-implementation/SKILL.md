# grill-implementation

実装前に、依頼・既存の合意・コードから決まることを確認し、ユーザー固有の未決事項だけを整理する。既存コードで答えられることは調べ、routine details は既存パターンに従って判断する。

## 使うとき

- 要求が不明で、スコープ・挙動・受け入れ条件などにユーザー固有の判断が残っているとき。
- ユーザーがインタビューや方針の壁打ちを明示的に依頼したとき。
- 要件が明確、方針が既承認、または既存パターンで決められる作業は起動せず通常の実装へ進む。
- 問題の再構成や複数案の比較を明示的に求められた場合だけ `derive-optimal-solution` を使う。実装依頼から自動的に連鎖させない。

## 進め方

1. タスク・Issue・ドキュメントを読み、関連コードと既存パターンを調べる。既知の事実、既承認の方針、委任された範囲を先に確定する。
2. スコープ、ユーザー向け挙動、受け入れ条件、または不可逆・外部影響のある判断に関わる未決事項だけを列挙する。リポジトリや文書から決まることは質問しない。
3. 必要な質問だけを回答しやすい単位で提示する。選択肢がある場合は推奨と短い根拠を添える。ユーザーが「任せる」と委任した routine details は既存実装から決め、承認を取り直さない。
4. 回答を受けたら決定を記録して進める。未決事項が一箇所だけをブロックするならそこだけ保留し、独立して進められる作業は続ける。
5. 実装に必要なユーザー固有の判断がなくなったら、スコープ・決定事項・参照した既存実装・残る保留だけを短くまとめ、追加の最終承認を求めず実装へ進む。ユーザーが最終確認を明示した場合や、別の公開・破壊的操作の承認が必要な場合はその指示を守る。

## 出力

必要に応じて次を示す。

- 確定したスコープ（作るもの、作らないもの）
- ユーザーが決めた方針と、その根拠
- 調査した既存パターン
- 未決事項と、それによって保留する範囲
- 次に進める作業

質問数、軸の数、文書の行数を収束条件にしない。必要な判断が済んだ時点で終了する。

## 合意とスコープの扱い

- 過去の明示的な合意や承認を有効な前提として扱い、同じ内容を聞き直さない。
- 「任せる」は、既存の規約とパターンの範囲で判断を委任されたものとして扱う。ユーザーの目的や受け入れ条件を変える複数案だけを確認する。
- 元の依頼の目的・スコープ・許可された情報の範囲を守る。無関係な機密情報を収集・開示せず、判断に不要な機能を追加しない。
- 仕様の不明点と、実装中に生じる routine details を分ける。前者だけを質問し、後者は安全な既存パターンで埋める。
