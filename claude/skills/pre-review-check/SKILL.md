# Pre-review check

差分と受入条件を確認し、根拠のある問題を外部レビューの前に解消する。
判定・スコープ・Finding ID の共通基準は [review-policy](../../rules/review-policy.md)。
ユーザーが確認だけを依頼した場合は報告で止め、修正を依頼されている場合はその範囲で直す。

## 1. 対象を確定する

最初に `git status --short` を確認し、ユーザー指定の staged / commit / branch / PR を優先する。
指定がなければローカル変更を対象とする。tracked は `git diff HEAD`、
untracked は `git ls-files --others --exclude-standard` から今回の変更を選び、内容も読む。
ステージ済みだけの依頼は `git diff --cached` に限定する。

branch / PR の base・head・merge-base の決め方は review-policy の「diff baseline の導出」に従う。
`main` や現在の `HEAD` をレビュー対象と決めつけない。
比較範囲・対象ファイルを一度確定して記録し、その差分を後続で共有する。
依頼・会話・Issue にある受入条件と、対象に適用されるローカル規約を集める。

## 2. 適用するカテゴリを選ぶ

次の11カテゴリすべてに適用可否を付け、対象がある行だけ調べる。
対象外は `N/A`。対象があるが必要な資料・ツールにアクセスできない場合は `確認不可` と理由を残す。
既にこの実行で読んだ規約や同じ差分の検証結果は再利用する。

| # | 対象がある場合に確認すること | 詳細を読む条件 |
| --- | --- | --- |
| 1 | 関連Issueの受入条件・親子間の合意 | Issueが指定されていれば [issue-context](references/issue-context.md) |
| 2 | 既存のドメイン型・命名・enumと、新規定義や利用箇所の一致 | 型・語彙の変更時に定義と呼び出し元を検索 |
| 3 | 置換・削除した機能の移行先。導線・条件表示・権限を含む | 置換・削除時に旧実装と利用元を確認 |
| 4 | 指定されたFigma要素と実装の対応 | デザイン指定があれば [ui-checks](references/ui-checks.md) |
| 5 | UIコンポーネントのvariant・propsと対応スタイル | UI変更なら同上 |
| 6 | 操作できるボタン・リンクの実動作 | 操作要素の変更なら同上 |
| 7 | fixture・機密情報・ダミーデータの本番到達経路 | データ追加時に既存mock境界とbuild/import経路を確認 |
| 8 | そのプロジェクトで実際に宣言された規約 | 対象のAGENTS.md・rules・近い既存実装を確認 |
| 9 | 外部入力→sink、認可、機密出力、CIの信頼境界 | 実行コード・設定・CI変更なら [security-sinks](../cr/references/security-sinks.md) の該当言語のみ |
| 10 | 配線漏れ、重複、不要な分岐・拡張、未使用コード、fallbackの根拠 | コード変更なら [core-standards](../../rules/core-standards.md) の「コーディング基準」「AI 生成コード検証」 |
| 11 | 非同期UIのLoading/Error/Empty/NormalとHookの呼び出し順序 | 非同期UI変更なら [ui-checks](references/ui-checks.md) |

コードのあるカテゴリは `rg` と実ファイル、既存のlint・型検査・テストで裏付ける。
文字列が一致しただけで違反にせず、使用箇所・データ経路・適用規約を追う。
MSW、Storybook、CSS Modules、props分割代入禁止などを全プロジェクトに課さない。
架空のfixture名を実在のPIIと断定しない。機密性と、本番でmockを返す動作不良は別に判定する。
認可欠落の指摘には、保護対象と要求権限の根拠が必要。未認証という事実だけで公開APIを違反にせず、契約が不明なら確認不可として残す。

## 3. 修正・検証する

実在する問題だけに `PRC-001` 形式のIDを付け、severity、file:line、影響、修正案を残す。
正常カテゴリをFindingとして水増ししない。再確認では同じ問題のIDを引き継ぐ。

修正したら影響するカテゴリと必要なプロジェクト検証を再実行する。
新たに変更した経路も対象へ加える。既存の成功結果は同じ対象内容・検査条件のときだけ再利用する。
同じ問題が解消しなければ別の方法を1〜2回検討し、未解決の根拠を報告する。
スキル全体や外部レビューを自動で繰り返さない。

## 4. 補助チェックを回す

Codex は有限リソースなので、Claude 側で潰せるものはここで潰してから外部レビューに渡す。
同じ観点で `/similarity-check`、`/ponytail-review`、`/simplify` を重ねて起動しない。

- `/ponytail-review`: **コード変更があれば既定で実行する**。過剰設計・不要な抽象・冗長なコメントは
  自分の書いたものほど気づけない。報告から必要な修正を選ぶ。
- `/similarity-check`: 新規ファイル追加・既存実装のコピー・同種処理の横展開があれば実行する。
  対象言語・変更ファイルと関連実装に限定する。結果を読んで責務が同じ場合だけ統合する。
- `/simplify`: ユーザーが簡素化を依頼し、その環境で利用できる場合。これは review ではなく fix なので、
  回すなら外部レビューより前に回して、整った差分をレビューさせる。

docsのみ、実行済み、対象なし、ツール未導入なら理由付きでスキップする。
既定で実行するものをスキップした場合は、報告にその理由を書く。
補助ツールを入れるためにインストールを始めない。変更後は影響範囲の検証を行う。

## 5. 判定・報告する

- `BLOCKED`: スコープ内の未解決 `critical` / `major` がある。
- `INCOMPLETE`: 上記の問題はないが、対象差分・必須の受入条件・必要な検証に確認不可が残る。未確認を合格に数えない。
- `PASSED`: 必要な検証が済み、`critical` / `major` がない。`minor` は改善提案として残せる。

既定の補助チェックは §4 の条件（対象なし・実行済み・ツール未導入・docsのみ）でしかスキップできない。
「今回は要らない」という判断でスキップしない。環境要因で回せないことがあるため未実行そのものは
`INCOMPLETE` にしないが、スキップした事実と理由は報告に残す。
[report](references/report.md) の短い形式で、対象、判定、Finding、11カテゴリの結果、検証と未確認、次の行動を報告する。
`/codex:review` の実行・回数・承認は [codex-review-policy](../../rules/codex-review-policy.md) に従い、このスキル内では起動しない。
