# grill-implementation

実装に入る前に、書き手の頭の中にある暗黙の仕様を全部引きずり出して合意に変える。

**インタビューの進め方そのものは `/grilling` に従う**（決定ツリーをラウンド単位で聞く、各質問に推奨回答を添える、環境から分かる事実は自分で調べる、フロンティアが空になるまで続ける）。このスキルはその上に、実装着手のための契約 — 詰めるべき決定軸、合意サマリー、スキップ基準、合意の保持 — を載せる。

## 質問の優先順位

上から順に詰める。上位が未確定のまま下位に進まない。

1. **スコープ**: 何を作る / 何を作らない。既存の何を変える / 変えない
2. **配置**: どのディレクトリ、どのファイル。既存のどのモジュール構造に寄せるか
3. **既存再利用**: 既存コンポーネント / 関数 / hook の再利用先。新規作成 vs 再利用の判断
4. **公開 API 形状**: 関数シグネチャ、型定義、props、URL / query / path params
5. **データフロー**: state 管理、API、型変換、副作用のタイミング
6. **エッジケース**: loading / error / empty / boundary / 権限 / 認可
7. **テスト**: テストで何を担保するか、どのレベル（unit / integration / storybook）
8. **ロールアウト**: feature flag / 段階的リリース / 監視

## 禁止事項

- 質問せずに実装に進む
- 同じ疑問を別のセッションで再度質問する（このスキルで一度解決したら合意事項としてメモに残す）
- 「細かいところは後で」と曖昧さを温存する

## ワークフロー

### Phase 0: 問題の再構成判定（任意・derive-optimal-solution との接続）

Phase 1 の前に、入力が `derive-optimal-solution` の発動条件（評価・再考語、症状対処止まりの疑い、複数レイヤーにまたがる問題等。詳細は同スキルの「発動条件」節）に該当すれば **`derive-optimal-solution` を先に走らせる**。

`derive-optimal-solution` の出力(問題の再構成・推奨案・選択しなかった案の却下理由)が確定し、ユーザーが方向性に合意してから Phase 1 に進む。

スキップ条件: タスク記述に「具体的に何を作るか」が明示されており、判断対象が「どう作るか」のみ(= 解空間が確定済み)。

### Phase 1: 入力の把握

タスク記述 / Issue / Figma URL / PRD を読む。`git grep` や `Read` で既存の関連コードを先に把握する。

### Phase 2: 決定ツリーの構築

優先順位上位から順に、未確定な分岐を列挙する。各分岐について:

- **ユーザーに聞く**: コードベース / ドキュメントでは決まらない、本人の意図 / ビジネス判断に依存する質問
- **自分で調べる**: Grep / Read / `gh issue view` / Figma `get_design_context` で答えが出せる質問
- **codex に下読みさせる**（Claude Code 環境のみ）: plan・設計ドキュメントが既に文書として存在するなら、`codex:rescue` subagent に**非同期で**投げて矛盾・穴・リスクの指摘を回収し、決定ツリーの分岐に統合する。ユーザーへのインタビュー自体は移譲しない。回収を待たずに Phase 3 を開始してよい（指摘は途中合流）

### Phase 3: インタビューで解決

`/grilling` のラウンド方式で聞く（質問の書式・推奨回答の添え方・フロンティアの回し方は `/grilling` が SSOT）。各質問には、選んだ根拠をコードベースの既存パターン・制約・リスクから 1〜2 行で添える。

ユーザーの回答を受けたら、**合意事項をチャットの本文に明文化して記録**（後の Phase 5 で参照）。Task 管理ツールがあれば併用する。

### Phase 4: 収束判定

以下すべてを満たしたら grill-implementation を終え、実装フェーズに進む:

- 優先順位 1〜7（ロールアウト以外）の各軸で、未確定分岐が 0
- 合意事項がタスク管理機能 / メモ / チャットに明文化されている

実装着手の明示承認はここでは取らない。Phase 5 のサマリーに対して 1 回だけ取る（「まあいいよ」のような消極承認は要追い質問）。

### Phase 5: サマリー提示

実装に入る直前に、合意事項を箇条書きで提示する（後で「言ってない」「変わった」を防ぐ）:

```
## grill-implementation 合意サマリー

### スコープ
- 作る: <箇条書き>
- 作らない: <箇条書き>

### 主要決定
- <軸名>: <決定内容> (理由: <根拠>)
- <軸名>: <決定内容>

### 参照した既存実装
- <path>: <何を参考にする / コピーする>

### 保留事項
- <必要なら。実装中に追加質問する可能性があるもの>
```

## Output Contract

grill-implementation は **対話スキル** であり、最終成果物は **Phase 5 のサマリー**。
これを貼り付けて「この内容で進めますか」とユーザーに最終確認する。ユーザーが明示的に承認したら grill-implementation 終了 → 実装スキル側の次フェーズへ。

## スキップ可能な条件

以下すべてを満たす場合のみ grill-implementation をスキップしてよい:

- 変更が **1 ファイル 3 行以下** の軽微な修正
- ユーザーが具体的なファイル / 行 / 修正内容まで明示している
- **コードベース調査なしで修正が一意に決まる**（typo 修正、文言変更、定数値変更など。新規コンポーネント追加・パターン選択を伴う変更はスキップ不可）

判断に迷ったらスキップしない。無駄な質問より、あとで手戻りするほうが損失が大きい。

## 合意事項の保持（最重要）

Phase 5 サマリーで合意された内容は **実装フェーズ完了まで不変** として扱う。

- 実装中に判断が分かれる細部に直面したら、合意内容に含まれていれば従う
- 含まれていない（= 保留事項 or 当初の想定外）なら、**独断で埋めない**。該当箇所だけ保留して質問し、合意済みで独立して進められる領域はそのまま進める（全体を止めるのは、その判断なしに他が書けない場合だけ）
- 「やっぱり X で」と実装中に方針転換する場合、サマリーを書き換えてからユーザー承認を再取得

## Red flags（自分に対する警告）

| サイン | 対応 |
| --- | --- |
| 質問せずに実装に入ろうとしている | 止まる。Phase 2 に戻る |
| 推奨回答を書かず選択肢だけ並べている | 書き直す。推奨を出すのが責務 |
| ユーザーが「任せる」「お任せ」と言った | 任されたと解釈せず、具体案を Phase 5 サマリー形式で再提示して明示承認を待つ |
| **Phase 5 サマリー提示後に**ユーザーが「いいよ」「OK」と短く返した | 合意成立。サマリーに書いた全項目への合意とみなし、細部の再質問はしない |
| Phase 3 の途中でユーザーが「それでいい」と返した | 個別分岐への回答であって実装着手の承認ではない。Phase 5 サマリーまで進む |
| 同じ質問に 2 回目の回答を求めている | 前の合意を忘れている。ログを再確認する |
| Phase 5 サマリーなしに実装に入った | 手戻りの原因。必ず書く |
| 実装フェーズで合意外の判断を迫られた | grill-implementation に戻る合図。独断で埋めない |
