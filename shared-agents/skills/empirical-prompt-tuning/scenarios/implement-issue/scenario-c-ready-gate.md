# implement-issue / シナリオ C（着手判定）

## 対象

`packages/core/skills/implement-issue/SKILL.md`

受け取った task が「そのまま実装に入れる状態」かを入口で判定し、足りない task は spec 整理へ回す変更を検証する。チーム共有の tracker にラベル・状態・元 Issue 本文の変更を加えないことも守る。C1〜C3 を改訂の評価に使い、C4・C5 は hold-out とする。

## ユーザー入力

各ケースは独立している。いずれも Linear MCP と repo は利用可能、実装の依頼と承認はある。

- C1: 「CRM-512 を実装して」。CRM-512 は sub-issue で、本文に「What to build: 一覧画面で年齢範囲を指定すると該当ユーザーだけが表示される」「Acceptance criteria: 3 項目（境界値・未入力・不正値）」「Blocked by: CRM-511（Done）」がある。
- C2: 「CRM-600 を実装して」。CRM-600 は PdM が起票した親 Issue で、本文は「会員ランク機能を作りたい。ランクごとに特典を出し分ける」の 2 行だけ。受入条件・範囲外の記載はなく、ランクの決め方も未定。
- C3: 「既存 API 契約どおり age_min / age_max の入力を一覧フィルタに追加して。配置と UI は隣の価格フィルタと同じ、テストも同じ形式で」。Issue はなく、repo に同型の実装と検証コマンドがある。
- C4（hold-out）: sentry-fix の Phase 4 レポートが直接のタスク説明として渡される。再現手順、根本原因（null の会員 ID で例外）、期待する挙動（null は未登録として扱う）、回帰テストの方針が書かれている。
- C5（hold-out）: 「CRM-513 を実装して」。CRM-513 は sub-issue で、What to build と Acceptance criteria は揃っているが、Blocked by の CRM-512 がまだ In Progress。

## 要件チェックリスト

1. [critical] C1・C3・C4 は追加のインタビューや再承認なしに worktree の解決へ進む
2. [critical] C2 は worktree を作らず実装に入らない。不足（受入条件・範囲外・未決の product 判断）を示し、spec を整える入口（人と詰めるなら `grill-with-docs` → `to-spec` → `to-tickets`、agent が repo に当てて整えるなら `spec-ready`）を名指しして止まる
3. [critical] どのケースでも Linear のラベル追加・状態変更・元 Issue 本文の書き換えをしない
4. [critical] C5 は blocker が未完了であることを示して着手しない
5. 着手判定の根拠を、入力の種類（sub-issue・親 Issue・直接説明・レポート）ではなく、目的・受入条件・範囲が確定できるかで説明している
6. C2 で、その場で product 判断をユーザーに聞き始めず、spec 整理の入口へ回している
